# SQL 10 — Indexes and Query Plans

An index is a sorted copy of some columns pointing back at the rows. The
database jumps to matches instead of reading the whole table. You write the
same SQL; the plan changes. `EXPLAIN` prints the plan PostgreSQL chose.
The numbers are estimates: startup cost, total cost, row count, and average
width. `EXPLAIN (ANALYZE, BUFFERS)` runs the query and adds real timings,
which change from run to run, so the plans here are plain `EXPLAIN`.

Primary keys and `UNIQUE` constraints already create indexes. A foreign
key does not. Index the child column, or a delete of the parent scans the
child table. Each extra index slows `INSERT`, `UPDATE`, and `DELETE` and
uses disk. Do not index everything. Drop the ones no plan uses. A tiny
table is often cheaper to scan than to probe. The planner knows that once
`ANALYZE` has written fresh statistics. `generate_series(1, n)` is the
integers from 1 through n, which is a handy way to load those rows.

A `Seq Scan` reads the heap. An `Index Scan` walks the index and fetches
the matching heap rows. An `Index Only Scan` can answer from the index
alone when every needed column is in it and the visibility map, filled by
`VACUUM`, says the pages are all-visible. A `Bitmap Index Scan` builds a
bitmap of matching pages and then visits the heap; the planner picks it
when many rows match. A `Sort` node appears when the index did not already
produce the `ORDER BY`.

## Without an index the plan is a sequential scan

Five thousand rows, and `user_id = 42` still reads the table. Nothing
narrower exists. `ANALYZE` first, or the row estimates are a default guess.

```sql file=n01.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i,
       CASE i % 4 WHEN 0 THEN 'login' WHEN 1 THEN 'view' WHEN 2 THEN 'buy' ELSE 'logout' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 5000) AS s(i);
ANALYZE event;
EXPLAIN SELECT note FROM event WHERE user_id = 42;
```

```text output
Seq Scan on event  (cost=0.00..98.50 rows=1 width=5)
  Filter: (user_id = 42)
```

## A selective lookup uses an Index Scan

`Index Cond` is the predicate the index applied. `note` is not in the
index, so this cannot be an index-only scan: the heap still supplies the
column. One matching row is selective enough that the index wins over the
sequential scan.

```sql file=n02.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i,
       CASE i % 4 WHEN 0 THEN 'login' WHEN 1 THEN 'view' WHEN 2 THEN 'buy' ELSE 'logout' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 5000) AS s(i);
CREATE INDEX event_user ON event (user_id);
ANALYZE event;
EXPLAIN SELECT note FROM event WHERE user_id = 42;
```

```text output
Index Scan using event_user on event  (cost=0.28..8.30 rows=1 width=5)
  Index Cond: (user_id = 42)
```

## A composite index serves its leftmost prefix

`(user_id, kind)` answers `user_id`, or `user_id` and `kind`, but not
`kind` alone. Put equality columns first, then the range or sort column.
`(a, b, c)` does not help a filter on `b` alone. A column with only a few
distinct values rarely deserves its own index. A partial index on the rare
value does.

```sql file=n03.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i,
       CASE i % 4 WHEN 0 THEN 'login' WHEN 1 THEN 'view' WHEN 2 THEN 'buy' ELSE 'logout' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 5000) AS s(i);
CREATE INDEX event_user_kind ON event (user_id, kind);
ANALYZE event;
EXPLAIN SELECT note FROM event WHERE user_id = 42 AND kind = 'buy';
EXPLAIN SELECT note FROM event WHERE kind = 'buy';
```

```text output
Index Scan using event_user_kind on event  (cost=0.28..8.30 rows=1 width=5)
  Index Cond: ((user_id = 42) AND (kind = 'buy'::text))
Seq Scan on event  (cost=0.00..98.50 rows=1250 width=5)
  Filter: (kind = 'buy'::text)
```

## An index in the right order avoids a sort

`ORDER BY kind` after `user_id = 7` matches the index order. With `LIMIT`,
the planner walks the index and stops. There is no `Sort` node. `ORDER BY
note` has no such index, so the plan sorts the sequential scan. The arrow
is the child of the node above it.

```sql file=n04.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT (i % 200) + 1,
       CASE i % 4 WHEN 0 THEN 'login' WHEN 1 THEN 'view' WHEN 2 THEN 'buy' ELSE 'logout' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 8000) AS s(i);
CREATE INDEX event_user_kind ON event (user_id, kind);
ANALYZE event;
EXPLAIN SELECT kind, note FROM event WHERE user_id = 7 ORDER BY kind LIMIT 5;
EXPLAIN SELECT note FROM event ORDER BY note;
```

```text output
Limit  (cost=0.28..15.86 rows=5 width=10)
  ->  Index Scan using event_user_kind on event  (cost=0.28..124.93 rows=40 width=10)
        Index Cond: (user_id = 7)
Sort  (cost=656.63..676.63 rows=8000 width=5)
  Sort Key: note
  ->  Seq Scan on event  (cost=0.00..138.00 rows=8000 width=5)
```

## A function on the column defeats the index

`lower(note) = 'n42'` cannot use an index on `note`. It can use an index
on `lower(note)`. The expression in the index and the expression in the
query have to match. A cast does the same damage when it is not the same
cast the index stored. Mark a custom function `IMMUTABLE` before you index
it; a function that depends on a setting is not allowed in an index.

```sql file=n05.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i,
       CASE i % 4 WHEN 0 THEN 'login' WHEN 1 THEN 'view' WHEN 2 THEN 'buy' ELSE 'logout' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 5000) AS s(i);
ANALYZE event;
EXPLAIN SELECT id FROM event WHERE lower(note) = 'n42';
CREATE INDEX event_note_lower ON event ((lower(note)));
ANALYZE event;
EXPLAIN SELECT id FROM event WHERE lower(note) = 'n42';
```

```text output
Seq Scan on event  (cost=0.00..111.00 rows=25 width=4)
  Filter: (lower(note) = 'n42'::text)
Index Scan using event_note_lower on event  (cost=0.28..8.30 rows=1 width=4)
  Index Cond: (lower(note) = 'n42'::text)
```

## A leading wildcard cannot use a btree index

`LIKE '%99'` has to look at every note. `EXPLAIN` prints `LIKE` as `~~`.
A prefix pattern such as `LIKE 'n4242%'` can use a btree index built with
`text_pattern_ops`. The default text operator class follows the database
collation and does not support prefix `LIKE`. The index condition is the
range from `'n4242'` up to `'n4243'`; the `Filter` line rechecks the
pattern.

```sql file=n06.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i,
       CASE i % 4 WHEN 0 THEN 'login' WHEN 1 THEN 'view' WHEN 2 THEN 'buy' ELSE 'logout' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 5000) AS s(i);
CREATE INDEX event_note_pat ON event (note text_pattern_ops);
ANALYZE event;
EXPLAIN SELECT id FROM event WHERE note LIKE '%99';
EXPLAIN SELECT id FROM event WHERE note LIKE 'n4242%';
```

```text output
Seq Scan on event  (cost=0.00..98.50 rows=202 width=4)
  Filter: (note ~~ '%99'::text)
Index Scan using event_note_pat on event  (cost=0.28..8.30 rows=1 width=4)
  Index Cond: ((note ~>=~ 'n4242'::text) AND (note ~<~ 'n4243'::text))
  Filter: (note ~~ 'n4242%'::text)
```

## A partial index stores only the rows you query

`WHERE kind = 'buy'` keeps the index small. The query must imply that
same predicate or the planner cannot use the index. The plan names
`event_buys` and does not repeat `kind = 'buy'`: the index already
guarantees it. The same predicate on `user_id` alone, with no other index
to help, is a sequential scan.

```sql file=n07.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i,
       CASE WHEN i % 50 = 0 THEN 'buy' ELSE 'view' END,
       make_date(2024, 1 + (i % 12), 1 + (i % 28)),
       'n' || i
FROM generate_series(1, 5000) AS s(i);
CREATE INDEX event_buys ON event (user_id) WHERE kind = 'buy';
ANALYZE event;
EXPLAIN SELECT note FROM event WHERE kind = 'buy' AND user_id = 100;
EXPLAIN SELECT note FROM event WHERE user_id = 100;
```

```text output
Index Scan using event_buys on event  (cost=0.14..8.16 rows=1 width=5)
  Index Cond: (user_id = 100)
Seq Scan on event  (cost=0.00..99.50 rows=1 width=5)
  Filter: (user_id = 100)
```

## A unique index is also a rule

`CREATE UNIQUE INDEX` rejects a second row with the same `note`. The notes
from the seed are already unique (`n1`, `n2`, ...), so inserting `n5`
again fails. A `UNIQUE` constraint builds the same kind of index.

```sql file=n08.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i, 'view', DATE '2024-01-01', 'n' || i
FROM generate_series(1, 50) AS s(i);
CREATE UNIQUE INDEX event_note_uq ON event (note);
-- expect-error
INSERT INTO event (user_id, kind, at, note) VALUES (1, 'view', DATE '2024-01-01', 'n5');
```

```text output
Error: duplicate key value violates unique constraint "event_note_uq"
```

## pg_indexes lists them, and ANALYZE records that it ran

`pg_indexes` is one row per index, including the primary key index
`event_pkey`. `indexdef` is the statement that would recreate it.
`ANALYZE` updates `pg_stat_user_tables.last_analyze`. Run it after a big
load, not before every query. Autovacuum also analyzes, but not in time
for a plan you are inspecting right now.

```sql file=n09.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
INSERT INTO event (user_id, kind, at, note)
SELECT i, 'view', DATE '2024-01-01', 'n' || i
FROM generate_series(1, 20) AS s(i);
CREATE INDEX event_user ON event (user_id);
CREATE INDEX event_user_kind ON event (user_id, kind);
CREATE INDEX event_note_lower ON event ((lower(note)));
CREATE INDEX event_buys ON event (at) WHERE kind = 'buy';
CREATE UNIQUE INDEX event_note_uq ON event (note);
ANALYZE event;
.headers on
SELECT indexname FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'event'
ORDER BY indexname;
SELECT (last_analyze IS NOT NULL) AS analyzed
FROM pg_stat_user_tables
WHERE relname = 'event';
```

```text output
indexname
event_buys
event_note_lower
event_note_uq
event_pkey
event_user
event_user_kind
analyzed
t
```

## Drop the indexes you do not want to maintain

After dropping the unique note index and the expression index, the primary
key index and `event_user` remain. Writes no longer update the two you
removed.

```sql file=n10.sql
CREATE TABLE event (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id int NOT NULL,
  kind text NOT NULL,
  at date NOT NULL,
  note text NOT NULL
);
CREATE INDEX event_user ON event (user_id);
CREATE INDEX event_note_lower ON event ((lower(note)));
CREATE UNIQUE INDEX event_note_uq ON event (note);
DROP INDEX event_note_uq;
DROP INDEX event_note_lower;
.headers on
SELECT count(*) AS indexes_left
FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'event';
```

```text output
indexes_left
2
```

## A foreign key does not create an index

`REFERENCES` is a constraint. It does not add an index on the child
column. A lookup or a parent delete then scans the child table. Create
the index yourself. Here `id` is not in `book_author`, so the plan is an
`Index Scan` that fetches the heap, not an index-only scan.

```sql file=n11.sql
CREATE TABLE author (id int PRIMARY KEY);
CREATE TABLE book (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  author_id int REFERENCES author (id)
);
INSERT INTO author SELECT i FROM generate_series(1, 5000) AS s(i);
INSERT INTO book (author_id) SELECT i FROM generate_series(1, 5000) AS s(i);
ANALYZE book;
EXPLAIN SELECT id FROM book WHERE author_id = 7;
CREATE INDEX book_author ON book (author_id);
ANALYZE book;
EXPLAIN SELECT id FROM book WHERE author_id = 7;
```

```text output
Seq Scan on book  (cost=0.00..85.50 rows=1 width=4)
  Filter: (author_id = 7)
Index Scan using book_author on book  (cost=0.28..8.30 rows=1 width=4)
  Index Cond: (author_id = 7)
```
