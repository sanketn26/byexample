# SQL 11 — Views and Triggers

A view is a saved query you use like a table: a named interface over the
real schema. A trigger is a PL/pgSQL function the database runs when rows
change. Use triggers for invariants (an audit row, a derived counter, a
guard). Do not hide business workflows in them. They are invisible to the
statement that fires them, which is a bad surprise later. Constraints
first, triggers second. Application code is easier to test; database rules
apply to every client.

A plain view stores no data. Its query runs every time, so a slow view is
a slow query. A `MATERIALIZED VIEW` stores the result and stays stale until
`REFRESH MATERIALIZED VIEW`. Name columns in the view. `integer PRIMARY KEY`
does not generate values. When an insert omits the id, declare
`GENERATED BY DEFAULT AS IDENTITY`. `BY DEFAULT` still accepts an explicit
id. `SELECT *` in a view is a poor interface: add the columns you mean.

## A view hides columns and collapses rows

`dept_summary` is the aggregate. `emp_public` omits salary. You select
from the view as if it were a table.

```sql file=n01.sql
CREATE TABLE emp (
  id integer PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
INSERT INTO emp VALUES
  (1, 'Ada', 'eng', 150), (2, 'Linus', 'eng', 120), (3, 'Don', 'sales', 90);
CREATE VIEW dept_summary AS
  SELECT dept, count(*) AS people, sum(salary) AS payroll FROM emp GROUP BY dept;
CREATE VIEW emp_public AS SELECT id, name, dept FROM emp;
.headers on
SELECT * FROM dept_summary ORDER BY dept;
SELECT * FROM emp_public ORDER BY id;
```

```text output
dept|people|payroll
eng|2|270
sales|1|90
id|name|dept
1|Ada|eng
2|Linus|eng
3|Don|sales
```

## A view is live

It does not keep a copy. Insert a row into `emp` and the next select from
the view sees it.

```sql file=n02.sql
CREATE TABLE emp (
  id integer PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
INSERT INTO emp VALUES
  (1, 'Ada', 'eng', 150), (2, 'Linus', 'eng', 120), (3, 'Don', 'sales', 90);
CREATE VIEW dept_summary AS
  SELECT dept, count(*) AS people, sum(salary) AS payroll FROM emp GROUP BY dept;
INSERT INTO emp VALUES (4, 'Peggy', 'sales', 95);
.headers on
SELECT * FROM dept_summary WHERE dept = 'sales';
```

```text output
dept|people|payroll
sales|2|185
```

## A materialized view is a snapshot

`REFRESH` is what copies the new row in. Until then the stored result still
shows one salesperson. Refresh replaces the whole snapshot. It takes a lock
and reruns the query. `CONCURRENTLY` needs a unique index and still is not
free. Use it when the query is expensive and slightly stale is acceptable.

```sql file=n03.sql
CREATE TABLE emp (
  id integer PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
INSERT INTO emp VALUES
  (1, 'Ada', 'eng', 150), (2, 'Linus', 'eng', 120), (3, 'Don', 'sales', 90);
CREATE MATERIALIZED VIEW dept_summary AS
  SELECT dept, count(*) AS people, sum(salary) AS payroll FROM emp GROUP BY dept;
INSERT INTO emp VALUES (4, 'Peggy', 'sales', 95);
.headers on
SELECT * FROM dept_summary WHERE dept = 'sales';
REFRESH MATERIALIZED VIEW dept_summary;
SELECT * FROM dept_summary WHERE dept = 'sales';
```

```text output
dept|people|payroll
sales|1|90
dept|people|payroll
sales|2|185
```

## An AFTER trigger records the change

The trigger calls a function. `RETURNS trigger` and `FOR EACH ROW` are what
make `OLD` and `NEW` exist. `UPDATE OF salary` fires only for that column.
`WHEN (OLD.salary <> NEW.salary)` skips a write that sets the same number,
and it is tested before the function runs. `INSERT` has only `NEW`.
`DELETE` has only `OLD`. Renaming Linus is not a salary change, so it
writes no audit row. The default timestamp is a fixed clock so the audit
does not depend on today. Return `NEW`. A trigger that updates another
table can fire more triggers. Watch for loops.

```sql file=n04.sql
CREATE TABLE emp (
  id integer PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
INSERT INTO emp VALUES
  (1, 'Ada', 'eng', 150), (2, 'Linus', 'eng', 120),
  (3, 'Don', 'sales', 90), (4, 'Peggy', 'sales', 95);
CREATE TABLE audit (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  at timestamp NOT NULL DEFAULT timestamp '2024-01-01',
  emp_id integer,
  action text,
  old_salary integer,
  new_salary integer
);
CREATE FUNCTION emp_salary_audit() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit (emp_id, action, old_salary, new_salary)
  VALUES (OLD.id, 'raise', OLD.salary, NEW.salary);
  RETURN NEW;
END;
$$;
CREATE TRIGGER emp_salary_audit
AFTER UPDATE OF salary ON emp
FOR EACH ROW
WHEN (OLD.salary <> NEW.salary)
EXECUTE FUNCTION emp_salary_audit();
UPDATE emp SET salary = salary + 10 WHERE dept = 'sales';
UPDATE emp SET name = 'Linus T.' WHERE id = 2;
.headers on
SELECT emp_id, action, old_salary, new_salary, at FROM audit ORDER BY id;
```

```text output
emp_id|action|old_salary|new_salary|at
3|raise|90|100|2024-01-01 00:00:00
4|raise|95|105|2024-01-01 00:00:00
```

## A BEFORE trigger can reject the change

`RAISE EXCEPTION` aborts the statement and rolls it back. Ada's salary
stays 150. The `WHEN` clause means the function runs only for a pay cut.
A `BEFORE` trigger that returns NULL skips that row instead of changing it.
Raising is the right tool when the write is illegal, not merely unwanted.

```sql file=n05.sql
CREATE TABLE emp (
  id integer PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
INSERT INTO emp VALUES
  (1, 'Ada', 'eng', 150), (2, 'Linus', 'eng', 120), (3, 'Don', 'sales', 90);
CREATE FUNCTION no_pay_cut() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'salary cannot decrease';
END;
$$;
CREATE TRIGGER no_pay_cut
BEFORE UPDATE OF salary ON emp
FOR EACH ROW
WHEN (NEW.salary < OLD.salary)
EXECUTE FUNCTION no_pay_cut();
-- expect-error
UPDATE emp SET salary = 1 WHERE id = 1;
.headers on
SELECT salary FROM emp WHERE id = 1;
```

```text output
Error: salary cannot decrease
salary
150
```

## Triggers keep a derived counter in step

`comment_ins` adds one. `comment_del` subtracts one, using `OLD.post_id`.
After inserting three comments and deleting one, the post shows 2. The
counter is only right if every change goes through these triggers. One
function can serve one trigger; they are separate objects.

```sql file=n06.sql
CREATE TABLE post (
  id integer PRIMARY KEY,
  title text,
  comment_count integer NOT NULL DEFAULT 0
);
CREATE TABLE comment (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  post_id integer,
  body text
);
CREATE FUNCTION comment_ins() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE post SET comment_count = comment_count + 1 WHERE id = NEW.post_id;
  RETURN NEW;
END;
$$;
CREATE FUNCTION comment_del() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE post SET comment_count = comment_count - 1 WHERE id = OLD.post_id;
  RETURN OLD;
END;
$$;
CREATE TRIGGER comment_ins
AFTER INSERT ON comment
FOR EACH ROW
EXECUTE FUNCTION comment_ins();
CREATE TRIGGER comment_del
AFTER DELETE ON comment
FOR EACH ROW
EXECUTE FUNCTION comment_del();
INSERT INTO post (id, title) VALUES (1, 'Hello');
INSERT INTO comment (post_id, body) VALUES (1, 'a'), (1, 'b'), (1, 'c');
DELETE FROM comment WHERE body = 'b';
.headers on
SELECT title, comment_count FROM post;
```

```text output
title|comment_count
Hello|2
```

## INSTEAD OF makes a view writable

A view of some columns of one table, with no join and no aggregate, is
auto-updatable. This one is not, in practice: `salary` is `NOT NULL` and
the view does not expose it, so a plain insert cannot succeed.
`INSTEAD OF` replaces the write. The function inserts into `emp` and forces
salary 50, ignoring the id the statement supplied. Return `NEW`.

```sql file=n07.sql
CREATE TABLE emp (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
INSERT INTO emp (name, dept, salary) VALUES ('Ada', 'eng', 150);
CREATE VIEW emp_public AS SELECT id, name, dept FROM emp;
CREATE FUNCTION emp_public_ins() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO emp (name, dept, salary) VALUES (NEW.name, NEW.dept, 50);
  RETURN NEW;
END;
$$;
CREATE TRIGGER emp_public_ins
INSTEAD OF INSERT ON emp_public
FOR EACH ROW
EXECUTE FUNCTION emp_public_ins();
INSERT INTO emp_public (id, name, dept) VALUES (NULL, 'Intern', 'eng');
.headers on
SELECT name, salary FROM emp WHERE name = 'Intern';
```

```text output
name|salary
Intern|50
```

## A view can hide soft-deleted rows

`live_doc` filters `deleted_at IS NULL`. The row is still in `doc`. Queries
through the view do not see it. `deleted_at` is a `date`, not text.

```sql file=n08.sql
CREATE TABLE doc (
  id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title text,
  deleted_at date
);
CREATE VIEW live_doc AS SELECT id, title FROM doc WHERE deleted_at IS NULL;
INSERT INTO doc (title) VALUES ('keep'), ('drop');
UPDATE doc SET deleted_at = date '2024-06-01' WHERE title = 'drop';
.headers on
SELECT * FROM live_doc;
```

```text output
id|title
1|keep
```

## The catalogs list views and triggers

`pg_trigger` stores triggers. `tgisinternal` hides the triggers that
implement foreign keys, so the list is the ones this script created.
`information_schema.views` lists views in `public`. Trigger names sort
first because `trigger` is before `view`. `DROP TRIGGER` needs the table.
Dropping a trigger does not drop its function. After the drops, those two
names are gone.

```sql file=n09.sql
CREATE TABLE emp (
  id integer PRIMARY KEY,
  name text NOT NULL,
  dept text,
  salary integer NOT NULL
);
CREATE VIEW dept_summary AS SELECT dept, count(*) AS people FROM emp GROUP BY dept;
CREATE VIEW emp_public AS SELECT id, name, dept FROM emp;
CREATE TABLE doc (id integer PRIMARY KEY, title text, deleted_at date);
CREATE VIEW live_doc AS SELECT id, title FROM doc WHERE deleted_at IS NULL;
CREATE FUNCTION noop() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  RETURN NULL;
END;
$$;
CREATE TRIGGER emp_salary_audit
AFTER UPDATE OF salary ON emp
FOR EACH ROW
EXECUTE FUNCTION noop();
CREATE TRIGGER no_pay_cut
BEFORE UPDATE OF salary ON emp
FOR EACH ROW
EXECUTE FUNCTION noop();
CREATE TABLE post (id integer PRIMARY KEY);
CREATE TABLE comment (id integer PRIMARY KEY, post_id integer);
CREATE TRIGGER comment_ins
AFTER INSERT ON comment
FOR EACH ROW
EXECUTE FUNCTION noop();
CREATE TRIGGER comment_del
AFTER DELETE ON comment
FOR EACH ROW
EXECUTE FUNCTION noop();
CREATE TRIGGER emp_public_ins
INSTEAD OF INSERT ON emp_public
FOR EACH ROW
EXECUTE FUNCTION noop();
.headers on
SELECT tgname AS name, 'trigger' AS kind
FROM pg_trigger
WHERE NOT tgisinternal
UNION ALL
SELECT table_name, 'view'
FROM information_schema.views
WHERE table_schema = 'public'
ORDER BY kind, name;
DROP VIEW live_doc;
DROP TRIGGER no_pay_cut ON emp;
SELECT count(*) AS still_there FROM (
  SELECT tgname AS name FROM pg_trigger
  WHERE NOT tgisinternal AND tgname IN ('live_doc', 'no_pay_cut')
  UNION ALL
  SELECT table_name FROM information_schema.views
  WHERE table_schema = 'public' AND table_name IN ('live_doc', 'no_pay_cut')
) s;
```

```text output
name|kind
comment_del|trigger
comment_ins|trigger
emp_public_ins|trigger
emp_salary_audit|trigger
no_pay_cut|trigger
dept_summary|view
emp_public|view
live_doc|view
still_there
0
```

<details><summary>Solution</summary>

```sql file=solution.sql
CREATE TABLE product (
  id integer PRIMARY KEY,
  name text NOT NULL,
  price integer NOT NULL,
  stock integer NOT NULL
);
CREATE TABLE price_log (product_id integer, old_price integer, new_price integer);
INSERT INTO product VALUES (1, 'pen', 100, 50), (2, 'ink', 450, 5), (3, 'pad', 300, 0);

CREATE VIEW in_stock AS SELECT id, name, price FROM product WHERE stock > 0;

CREATE FUNCTION price_changed() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO price_log VALUES (OLD.id, OLD.price, NEW.price);
  RETURN NEW;
END;
$$;
CREATE TRIGGER price_changed
AFTER UPDATE OF price ON product
FOR EACH ROW
WHEN (OLD.price <> NEW.price)
EXECUTE FUNCTION price_changed();

CREATE FUNCTION no_free() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'price must be positive';
END;
$$;
CREATE TRIGGER no_free
BEFORE UPDATE OF price ON product
FOR EACH ROW
WHEN (NEW.price <= 0)
EXECUTE FUNCTION no_free();

UPDATE product SET price = price + 50 WHERE id IN (1, 2);
-- expect-error
UPDATE product SET price = 0 WHERE id = 3;

CREATE TABLE t (name text, ok boolean CHECK (ok));
INSERT INTO t VALUES ('view', (
  SELECT string_agg(name, ',' ORDER BY id) FROM in_stock
) IS NOT DISTINCT FROM 'pen,ink');
INSERT INTO t VALUES ('log', (
  SELECT string_agg(product_id::text || ':' || old_price::text || '>' || new_price::text,
                     ',' ORDER BY product_id)
  FROM price_log
) IS NOT DISTINCT FROM '1:100>150,2:450>500');
INSERT INTO t VALUES ('guard', (
  SELECT price FROM product WHERE id = 3
) IS NOT DISTINCT FROM 300);
SELECT 'PASS ' || name FROM t ORDER BY name;
```
