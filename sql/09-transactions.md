# SQL 09 — Transactions

A transaction groups statements so they succeed or fail together
(atomicity), leave valid data (consistency), hide half-done work
(isolation), and survive a crash (durability). The classic case is a
transfer: debit and credit both happen, or neither does.

Outside an explicit transaction, every statement is its own transaction
and commits if it succeeds. One transaction around a bulk load avoids a
commit per row. Keep it short. A transaction waiting on a person, an HTTP
call, or a sleep holds locks and blocks everyone else.

The default isolation level is `read committed`: each statement sees rows
committed before that statement started. `REPEATABLE READ` keeps one
snapshot for the whole transaction. `SERIALIZABLE` aborts a transaction
that would not fit a serial order, with SQLSTATE `40001`. Retry the whole
transaction, and make the write idempotent. Ask for a level at the start:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

In a session you write `BEGIN`, the statements, then `COMMIT` or
`ROLLBACK`. A `DO` block is one transaction too: it commits if the block
finishes, and it rolls back if the block raises and nobody catches the
error. These lessons use `DO` so the whole transaction is one statement.
`BEGIN` inside the block starts a PL/pgSQL subtransaction, which is the
same mechanism as `SAVEPOINT` and `ROLLBACK TO SAVEPOINT`. A `DO` block
cannot run the SQL command `ROLLBACK`.

## A finished block commits every write in it

Both balance updates and the ledger row land together. After the block
ends, other connections can see them. Stop at `COMMIT` in a session; here
the end of the block is the commit.

```sql file=n01.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
CREATE TABLE ledger (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  from_id int,
  to_id int,
  amount int
);
INSERT INTO account VALUES (1, 'ada', 100), (2, 'bob', 50);
DO $body$
BEGIN
  UPDATE account SET balance = balance - 30 WHERE id = 1;
  UPDATE account SET balance = balance + 30 WHERE id = 2;
  INSERT INTO ledger (from_id, to_id, amount) VALUES (1, 2, 30);
END
$body$;
.headers on
SELECT owner, balance FROM account ORDER BY id;
SELECT amount FROM ledger ORDER BY id;
```

```text output
owner|balance
ada|70
bob|80
amount
30
```

## An error with no handler rolls the whole block back

The first update would debit 30. The second would make the balance
negative, so `CHECK` rejects it and the block fails. PostgreSQL then
undoes every write in that transaction, including the debit that had
already run. The credit never happens. In a session the same failure
aborts the transaction: further commands fail with `current transaction
is aborted, commands ignored until end of transaction block` until you
`ROLLBACK`.

```sql file=n02.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'ada', 100), (2, 'bob', 50);
-- expect-error
DO $body$
BEGIN
  UPDATE account SET balance = balance - 30 WHERE id = 1;
  UPDATE account SET balance = balance - 500 WHERE id = 1;
  UPDATE account SET balance = balance + 500 WHERE id = 2;
END
$body$;
.headers on
SELECT owner, balance FROM account ORDER BY id;
```

```text output
Error: new row for relation "account" violates check constraint "balance_nonneg"
owner|balance
ada|100
bob|50
```

## A subtransaction rolls back only the recent part

The nested `BEGIN` is a savepoint. `RAISE EXCEPTION` undoes that nested
block, the handler runs, and the inserts from the outer block remain.
`WHEN raise_exception` catches that `RAISE` and not a check violation.
In a session the same split is `SAVEPOINT risky`, the risky statement,
then `ROLLBACK TO SAVEPOINT risky`.

```sql file=n03.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
CREATE TABLE ledger (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  from_id int,
  to_id int,
  amount int
);
INSERT INTO account VALUES (1, 'ada', 100), (2, 'bob', 50);
DO $body$
BEGIN
  INSERT INTO ledger (from_id, to_id, amount) VALUES (1, 2, 30);
  INSERT INTO ledger (from_id, to_id, amount) VALUES (1, 2, 1);
  BEGIN
    INSERT INTO ledger (from_id, to_id, amount) VALUES (1, 2, 999);
    RAISE EXCEPTION 'undo 999';
  EXCEPTION
    WHEN raise_exception THEN
      NULL;
  END;
END
$body$;
.headers on
SELECT amount FROM ledger ORDER BY id;
```

```text output
amount
30
1
```

## You can read your own uncommitted writes

Inside the nested block the balances are already zero: a transaction sees
its own changes. The variable `s` lives in the block's memory, so it still
holds 0 after the subtransaction rolls back. The table does not. The sum
is 150 again.

```sql file=n04.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'ada', 100), (2, 'bob', 50);
CREATE TABLE seen (label text, total int);
DO $body$
DECLARE
  s int;
BEGIN
  BEGIN
    UPDATE account SET balance = 0;
    SELECT sum(balance) INTO s FROM account;
    RAISE EXCEPTION 'undo';
  EXCEPTION
    WHEN raise_exception THEN
      INSERT INTO seen VALUES ('inside_tx', s);
  END;
END
$body$;
.headers on
SELECT label, total FROM seen;
SELECT sum(balance) AS after_rollback FROM account;
```

```text output
label|total
inside_tx|0
after_rollback
150
```

## Do the check and the change in one statement

Reading a balance in the application, subtracting, and writing it back
loses updates when two clients interleave. `balance = balance - 60 WHERE
balance >= 60` is one atomic statement. The second update matches no row.
`GET DIAGNOSTICS ... ROW_COUNT` is 0, which means the guard refused.
`SELECT ... FOR UPDATE` locks the row when you must read it before a later
statement in the same transaction. The lock lasts until the transaction
ends. `LOCK TABLE account IN SHARE ROW EXCLUSIVE MODE` locks the whole
table; prefer the row lock.

```sql file=n05.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'ada', 70), (2, 'bob', 80);
CREATE TABLE log (step int, rows_changed int);
DO $body$
DECLARE
  n int;
  b int;
BEGIN
  SELECT balance INTO b FROM account WHERE id = 1 FOR UPDATE;
  UPDATE account SET balance = balance - 60 WHERE id = 1 AND balance >= 60;
  GET DIAGNOSTICS n = ROW_COUNT;
  INSERT INTO log VALUES (1, n);
  UPDATE account SET balance = balance - 60 WHERE id = 1 AND balance >= 60;
  GET DIAGNOSTICS n = ROW_COUNT;
  INSERT INTO log VALUES (2, n);
END
$body$;
.headers on
SELECT step, rows_changed FROM log ORDER BY step;
SELECT owner, balance FROM account WHERE id = 1;
```

```text output
step|rows_changed
1|1
2|0
owner|balance
ada|10
```

## An idempotent write survives a retry

The second insert hits the primary key and does nothing. A retried
payment does not double-charge. Retry the whole transaction, not a single
statement in the middle of one. `ON CONFLICT DO NOTHING` is the idempotent
form. `ON CONFLICT DO UPDATE` is the form that merges.

```sql file=n06.sql
CREATE TABLE payment (
  key text PRIMARY KEY,
  amount int
);
INSERT INTO payment VALUES ('order-77', 10) ON CONFLICT (key) DO NOTHING;
INSERT INTO payment VALUES ('order-77', 10) ON CONFLICT (key) DO NOTHING;
.headers on
SELECT count(*) AS payments FROM payment;
```

```text output
payments
1
```

## The default isolation level is read committed

`current_setting('transaction_isolation')` reports the level of this
transaction. `read committed` means a second statement in the same
transaction can see a row another session committed after the first
statement. `REPEATABLE READ` would keep the first snapshot.
`SERIALIZABLE` would rather fail the transaction than allow an anomaly.
Set either with `BEGIN ISOLATION LEVEL ...` before any other statement.

```sql file=n07.sql
.headers on
SELECT current_setting('transaction_isolation') AS isolation;
```

```text output
isolation
read committed
```

## DDL rolls back with the transaction

`CREATE TABLE` inside a block disappears if the block rolls back. A
migration can create a table, copy rows, and undo the whole thing when a
later check fails. The nested handler below throws the create away and
lets the outer block finish.

```sql file=n08.sql
DO $body$
BEGIN
  BEGIN
    CREATE TABLE temp_experiment (x int);
    RAISE EXCEPTION 'undo';
  EXCEPTION
    WHEN raise_exception THEN
      NULL;
  END;
END
$body$;
.headers on
SELECT count(*) AS tables_named_temp_experiment
FROM information_schema.tables
WHERE table_schema = 'public' AND table_name = 'temp_experiment';
```

```text output
tables_named_temp_experiment
0
```

```sql file=exercise.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'ada', 100), (2, 'bob', 50), (3, 'cy', 0);

-- 1. Transfer 40 from ada (1) to cy (3) in one DO block, so both updates
--    commit together.
-- 2. Try to transfer 500 from bob (2) to cy (3) in one DO block. The debit
--    violates the CHECK. Mark that block with -- expect-error. The block
--    fails, so the credit never lands and bob stays at 50.
-- 3. Take 10 from bob (2) with ONE guarded UPDATE that only succeeds if bob
--    has at least 10 (no separate SELECT).
-- TODO: write the statements here

INSERT INTO grade VALUES ('ada',  (SELECT balance FROM account WHERE id = 1) = 60);
INSERT INTO grade VALUES ('cy',   (SELECT balance FROM account WHERE id = 3) = 40);
```

<details><summary>Solution</summary>

```sql file=solution.sql
CREATE TABLE account (
  id int PRIMARY KEY,
  owner text NOT NULL,
  balance int NOT NULL CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
INSERT INTO account VALUES (1, 'ada', 100), (2, 'bob', 50), (3, 'cy', 0);

DO $body$
BEGIN
  UPDATE account SET balance = balance - 40 WHERE id = 1;
  UPDATE account SET balance = balance + 40 WHERE id = 3;
END
$body$;

-- expect-error
DO $body$
BEGIN
  UPDATE account SET balance = balance - 500 WHERE id = 2;
  UPDATE account SET balance = balance + 500 WHERE id = 3;
END
$body$;

UPDATE account SET balance = balance - 10 WHERE id = 2 AND balance >= 10;

CREATE TABLE grade (name text, ok boolean NOT NULL CHECK (ok));
INSERT INTO grade VALUES ('ada',  (SELECT balance FROM account WHERE id = 1) = 60);
INSERT INTO grade VALUES ('cy',   (SELECT balance FROM account WHERE id = 3) = 40);
INSERT INTO grade VALUES ('bob',  (SELECT balance FROM account WHERE id = 2) = 40);
INSERT INTO grade VALUES ('sum',  (SELECT sum(balance) FROM account) = 140);
SELECT 'PASS ' || name FROM grade;
```
