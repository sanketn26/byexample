# SQL 07 — Changing Data: INSERT, UPDATE, DELETE, UPSERT

Reads are forgiving. Writes are not. `UPDATE` and `DELETE` without a
`WHERE` touch every row. Write the `WHERE` first, or run it as a `SELECT`
and then change the verb. Wrap a risky change in a transaction (lesson 09).

List columns on every `INSERT`. A later `ADD COLUMN` breaks an insert that
relied on column order. One multi-row `INSERT` is one statement and one
round trip. Deleting a parent that still has children is governed by
foreign keys (lesson 08), which PostgreSQL enforces.

A surrogate key is `GENERATED BY DEFAULT AS IDENTITY`: the column draws
its value from a sequence unless you supply one. `GENERATED ALWAYS` refuses
a supplied value unless you write `OVERRIDING SYSTEM VALUE`. Take ids from
`RETURNING`. Do not predict them.

## INSERT names its columns

Omitted columns take the default. `stock` defaults to 0. Several `VALUES`
tuples are one statement. The identity column starts at 1.

```sql file=n01.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
.headers on
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 100);
INSERT INTO item (sku, name) VALUES ('B-2', 'nut');
INSERT INTO item (sku, name, stock) VALUES ('C-3', 'screw', 40), ('D-4', 'washer', 15);
SELECT id, sku, name, stock FROM item ORDER BY id;
```

```text output
id|sku|name|stock
1|A-1|bolt|100
2|B-2|nut|0
3|C-3|screw|40
4|D-4|washer|15
```

## RETURNING gives back what the insert wrote

`RETURNING` is part of the write. It hands back the new row, including the
identity value, so the application does not issue a second query to guess
it. Columns come back in the order you list.

```sql file=n02.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES ('E-5', 'rivet', 5) RETURNING id, sku;
```

```text output
1|E-5
```

## INSERT ... SELECT copies rows

The select is the source. A `WHERE` decides which rows are copied. Later
changes to `item` do not change `low_stock`: it holds the values from the
moment of the insert.

```sql file=n03.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES
  ('A-1', 'bolt', 100), ('B-2', 'nut', 0), ('C-3', 'screw', 40), ('D-4', 'washer', 15);
CREATE TABLE low_stock (sku text, stock int);
INSERT INTO low_stock SELECT sku, stock FROM item WHERE stock < 20;
.headers on
SELECT sku, stock FROM low_stock ORDER BY sku;
```

```text output
sku|stock
B-2|0
D-4|15
```

## UPDATE can read the old value

`stock = stock + 10` uses the value before this statement. `RETURNING`
lists each row that changed. `WHERE stock > 0` is what keeps the second
update from touching every row. Wrap `RETURNING` in a CTE when you need
the rows in a stable order.

```sql file=n04.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES
  ('A-1', 'bolt', 100), ('B-2', 'nut', 0), ('C-3', 'screw', 40), ('D-4', 'washer', 15);
UPDATE item SET stock = stock + 10, updated = DATE '2024-06-01' WHERE sku = 'B-2'
RETURNING sku, stock, updated;
WITH changed AS (
  UPDATE item SET stock = stock - 1 WHERE stock > 0 RETURNING id, sku, stock
)
SELECT sku, stock FROM changed ORDER BY id;
```

```text output
B-2|10|2024-06-01
A-1|99
B-2|9
C-3|39
D-4|14
```

## UPDATE can use a subquery

The subquery decides which rows change. Here it is the skus that were
copied into `low_stock`. `upper` rewrites only those names.

```sql file=n05.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES
  ('A-1', 'bolt', 100), ('B-2', 'nut', 0), ('D-4', 'washer', 15), ('E-5', 'rivet', 5);
CREATE TABLE low_stock (sku text, stock int);
INSERT INTO low_stock SELECT sku, stock FROM item WHERE stock < 20;
UPDATE item SET name = upper(name) WHERE sku IN (SELECT sku FROM low_stock);
.headers on
SELECT sku, name FROM item WHERE sku IN ('D-4', 'E-5', 'A-1') ORDER BY sku;
```

```text output
sku|name
A-1|bolt
D-4|WASHER
E-5|RIVET
```

## least and greatest clamp a value

`least` returns the smaller argument, `greatest` the larger. Use them to
cap a stock level or to keep a balance from going below zero in an
expression. They do not replace a `CHECK`. The constraint is what still
rejects a bad write.

```sql file=n06.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0
);
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 100), ('B-2', 'nut', 0);
.headers on
SELECT sku, least(stock, 50) AS capped, greatest(stock, 10) AS floored
FROM item ORDER BY sku;
```

```text output
sku|capped|floored
A-1|50|100
B-2|0|10
```

## ON CONFLICT DO NOTHING skips a row that would break a constraint

A duplicate `sku` is a unique violation. `ON CONFLICT (sku) DO NOTHING`
swallows that row and leaves the old one in place. The statement succeeds.
The count stays 2. Any other error, such as a `NOT NULL` violation, still
aborts the statement.

```sql file=n07.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 100), ('B-2', 'nut', 0);
INSERT INTO item (sku, name) VALUES ('A-1', 'dup') ON CONFLICT (sku) DO NOTHING;
.headers on
SELECT count(*) AS still_two FROM item;
```

```text output
still_two
2
```

## ON CONFLICT DO UPDATE is an upsert

If `sku` is new, the row is inserted. If it exists, the `DO UPDATE` runs.
`excluded.stock` is the value that was turned away. The existing row is
`item.stock`: a bare `stock` is ambiguous in the `SET` list. The conflict
target must be a unique index or a primary key: here, `sku`.

```sql file=n08.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 100);
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 7)
ON CONFLICT (sku) DO UPDATE SET stock = item.stock + excluded.stock
RETURNING sku, stock;
INSERT INTO item (sku, name, stock) VALUES ('Z-9', 'new', 3)
ON CONFLICT (sku) DO UPDATE SET stock = item.stock + excluded.stock
RETURNING sku, stock;
```

```text output
A-1|107
Z-9|3
```

## An upsert changes only the columns you set

The conflicting row stays. Its identity value stays. Columns absent from
the `SET` list stay. Setting `name` and leaving `stock` alone is how you
rename a sku's label without zeroing the inventory. Prefer this to
deleting the row and inserting a replacement: delete would fire `ON DELETE`
actions and hand out a new id.

```sql file=n09.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 100);
INSERT INTO item (sku, name) VALUES ('A-1', 'replaced')
ON CONFLICT (sku) DO UPDATE SET name = excluded.name
RETURNING id, sku, name, stock;
```

```text output
1|A-1|replaced|100
```

## DELETE needs a WHERE

Look first with a `SELECT` that uses the same predicate. `RETURNING`
lists the rows that were removed. `TRUNCATE item` empties the table
without scanning each row and does not fire row-level `DELETE` triggers.
`TRUNCATE item RESTART IDENTITY` also resets the identity sequence, which
`DELETE` does not.

```sql file=n10.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0,
  updated date
);
INSERT INTO item (sku, name, stock) VALUES
  ('A-1', 'bolt', 100), ('E-5', 'rivet', 4), ('Z-9', 'new', 3);
.headers on
SELECT count(*) AS to_delete FROM item WHERE stock < 5;
WITH gone AS (
  DELETE FROM item WHERE stock < 5 RETURNING sku
)
SELECT sku FROM gone ORDER BY sku;
```

```text output
to_delete
2
E-5
Z-9
```

## GET DIAGNOSTICS reports how many rows the write touched

PostgreSQL does not return that count as a SQL function. Inside PL/pgSQL,
`GET DIAGNOSTICS n = ROW_COUNT` reads it for the statement just executed.
A `DO` block is an anonymous block in that language. After deleting every
`low_stock` row, the table is empty and `n` is how many went away.

```sql file=n11.sql
CREATE TABLE low_stock (sku text, stock int);
INSERT INTO low_stock VALUES ('B-2', 0), ('D-4', 15), ('E-5', 5);
DO $body$
DECLARE
  n int;
BEGIN
  DELETE FROM low_stock;
  GET DIAGNOSTICS n = ROW_COUNT;
  CREATE TABLE tally (deleted_rows int, remaining int);
  INSERT INTO tally VALUES (n, (SELECT count(*) FROM low_stock));
END
$body$;
.headers on
SELECT deleted_rows, remaining FROM tally;
```

```text output
deleted_rows|remaining
3|0
```

## TRUNCATE resets an identity; DELETE does not

`DELETE` leaves the sequence where it was, so the next insert continues
past the old ids. `TRUNCATE ... RESTART IDENTITY` starts the sequence
over. Both are transactional: a later rollback undoes them. `TRUNCATE`
takes a heavier lock. Use `DELETE` when you need row triggers or a
`WHERE`.

```sql file=n12.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text NOT NULL
);
INSERT INTO item (sku) VALUES ('A-1'), ('B-2');
DELETE FROM item;
INSERT INTO item (sku) VALUES ('C-3');
.headers on
SELECT id AS after_delete FROM item;
TRUNCATE item RESTART IDENTITY;
INSERT INTO item (sku) VALUES ('D-4');
SELECT id AS after_truncate FROM item;
```

```text output
after_delete
3
after_truncate
1
```

## Replace a table by building the next one and swapping names

`CREATE TABLE ... AS SELECT` copies the rows you want to keep. It does
not copy constraints, indexes, or identity. Add those afterwards if the
new table needs them. `DROP` the old table and `RENAME` the new one into
its place. Anything that did not match the `WHERE` is gone.

```sql file=n13.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0
);
INSERT INTO item (sku, name, stock) VALUES ('A-1', 'bolt', 100), ('B-2', 'nut', 9);
CREATE TABLE item_new AS SELECT id, sku, name FROM item WHERE stock > 50;
DROP TABLE item;
ALTER TABLE item_new RENAME TO item;
.headers on
SELECT id, sku, name FROM item;
```

```text output
id|sku|name
1|A-1|bolt
```

```sql file=solution.sql
CREATE TABLE item (
  id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku text UNIQUE NOT NULL,
  name text NOT NULL,
  stock int NOT NULL DEFAULT 0
);
INSERT INTO item (sku, name, stock) VALUES
  ('A-1', 'bolt', 100), ('B-2', 'nut', 0), ('C-3', 'screw', 40), ('D-4', 'washer', 15);

INSERT INTO item (sku, name, stock) VALUES ('E-5', 'rivet', 5);
UPDATE item SET stock = stock + 10 WHERE stock < 20;
INSERT INTO item (sku, name, stock) VALUES ('C-3', 'screw', 25)
  ON CONFLICT (sku) DO UPDATE SET stock = item.stock + excluded.stock;
INSERT INTO item (sku, name, stock) VALUES ('F-6', 'pin', 8)
  ON CONFLICT (sku) DO UPDATE SET stock = item.stock + excluded.stock;
DELETE FROM item WHERE stock <= 0;

CREATE TABLE grade (name text, ok boolean NOT NULL CHECK (ok));
INSERT INTO grade VALUES ('rows',  (SELECT count(*) FROM item) = 6);
INSERT INTO grade VALUES ('rivet', (SELECT stock FROM item WHERE sku = 'E-5') = 15);
INSERT INTO grade VALUES ('low',   (SELECT stock FROM item WHERE sku = 'B-2') = 10);
INSERT INTO grade VALUES ('upsert',(SELECT stock FROM item WHERE sku = 'C-3') = 65);
INSERT INTO grade VALUES ('new',   (SELECT stock FROM item WHERE sku = 'F-6') = 8);
```
